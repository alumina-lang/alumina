- [DONE] **`std/collections/vector.alu`** — unified 2026-05-12. `sysroot/std/collections/vector.alu` and `sysroot-aluminac/std/collections/vector.alu` are now byte-identical. The wholesale-swap segfault was diagnosed and fixed: the root cause was an aluminac compiler bug in `src/aluminac/parser/pass2.alu`, not anything in the Vector code itself.

  **Root cause.** Every `process_X` / `process_items_from` loop in `pass2.alu` held a `let pending = &self.ctx.pending_X[i]` borrow into a Vector while calling `build_X(node, pending)`. Inside `build_X` (for functions, enums, statics, macros) the body / init / value expression went through `ExprParser::parse_block`, which recursively runs `Pass1::new(...).visit_node(...)` for block-local items. The recursive Pass1 can push to **the same** `pending_X` Vector — and when that push reallocates, the outer borrow dangles. Subsequent reads of `pending.id` / `pending.name` / `pending.attributes` in `build_X` then return whatever data happened to land at the freed slot, producing the corrupted `Item` shape we observed (FnDef.id = code pointer, FnDef.attributes._ptr = small integer that previously held an Attribute tag).

  The old `sysroot-aluminac/std/collections/vector.alu` reserved a minimum capacity of 4 on first allocation (`if new_cap < 4 { new_cap = 4 }`). That floor masked the bug: by the time any realloc would have fired, the small per-file pending vectors had already stabilised in the 4-slot allocation, so pushes during recursion never moved the backing storage. sysroot's vector grows tighter (max(len*2, len+additional), no floor), so pending_functions now reallocs while the outer build_function is still running — making the dangling borrow visible.

  The deterministic repro on sysroot/std/mod.alu: items 0..1 (`assume`, `panic_assert`) parsed fine; item 2 was `internal::assert` whose body contains the nested `fn panic_assert` definition. Pass2 visited assert, captured `pending = &pending_functions[2]`, started parsing the body, the recursive Pass1 pushed `panic_assert` to `pending_functions`, the Vector realloc'd from capacity 4 to 8, and the outer `pending` reference became stale. `assert`'s FnDef.id / .name / .attributes / .span fields were then read off freed memory; build_lookup_tables later iterated those rotted attributes and segfaulted dereferencing a fake _ptr.

  **Root cause found (cross-protocol method resolution).** Eliminated by repro: `binary_search_by` with a by-value-capture closure works in isolation; `from_iter`'s by-ref mutating-capture map closure works (cumulative=1.0, weights=[0.5]); so `_cumulative_weights`/`_total_weight` are correct and the search is correct. The corruption is in `sample`'s `let sample: T = ... else when typing::is_floating_point::<T>() { rng.next_float() * self._total_weight }`. **`next_float` is a method of `protocol RngExt<Self: Rng<Self>>` (random/mod.alu:714), NOT of `protocol Rng`.** `WeightedIndex::sample<R: Rng<R>>(self, rng: &mut R)` bounds `R` by **`Rng<R>` only**. Aluminac resolves a method call on a protocol-bounded generic against the *declared bound's* protocol (`Rng`, which has no `next_float`) → unresolved → silently lowered to void/garbage → `sample` is garbage → wrong/inverted bucket. alumina-boot compiles & runs this (sysroot `make test-std` green) because it resolves protocol-default / mixin'd methods at **monomorphization against the concrete type** (the concrete rng mixes in both `Rng` and `RngExt`), not against the declared bound. Confirmed independently: `fn get_float<R: Rng<R>>(rng: &mut R) -> f64 { rng.next_float() }` fails with `could not resolve method 'next_float' on type 'Canned'`, while the same call inside the sysroot path silently degrades instead of erroring.

  This is a fundamental method-resolution divergence, not specific to random — it recurs wherever a generic bounded by a base protocol calls a method on a companion `Ext` protocol the concrete type mixes in (`std/sync`, `std/thread`, `std/net` all have base+ext pairs).

  **alumina-boot's algorithm (verified against src/alumina-boot/src/ir/mono/mod.rs — turnkey for the next session).** Crucial finding: alumina-boot does **NOT** do bound/super-bound-directed resolution at all. It is purely eager monomorphization + mixin-folding on the *concrete* type:
  - alumina-boot has **no IR placeholder type**. `lower_function_body` substitutes every generic param with its concrete IR type *before* lowering the body (`mod.rs:2448` `ast::Ty::Placeholder(id) => self.replacements.get(&id)`; `raise_type` `mod.rs:2647-2706` never yields a placeholder). So by the time `rng.next_float()` is lowered inside `sample::<…, Canned>`, `rng`'s type is the concrete `Item(Canned)`, never `R`/`Rng`.
  - `lower_method_call` (`mod.rs:4840`); resolution at `mod.rs:4876-4886`: `self.associated_fns(canonical)?.get(name).or(unified_fn)` where `canonical = ir_self_arg.ty.canonical_type()` (concrete).
  - `associated_fns_uncached` (`mod.rs:2784-2850`) builds the map from the concrete type's own assoc fns **then folds in every `mixin`** (`mod.rs:2830-2847`): for each mixin, `expand_mixin` it, and insert each mixin fn by name **iff not already present** (native shadows mixin; mixin order otherwise undefined). `Canned` has `next_float` purely because it did `mixin RngExt<Canned>` — the bound on `R` is never consulted for lookup.
  - Protocol-bound checking is entirely separate and lazy (`check_protocol_bounds` `mod.rs:827`, called at mono-item time on the concrete substituted type) — it never gates `.name` resolution. **Do NOT add a "given `R: Rng`, also search `RngExt` because `RngExt: Rng`" branch — that asymmetry does not exist in boot and is the wrong-shaped fix.**

  **The aluminac fix is one of two shapes — diagnose which first:**
  1. *If aluminac already substitutes `R`→concrete before lowering `sample`'s body* (likely — it mono's per type-args): then `rng`'s receiver type at the `next_float` call IS `Canned`, and the bug is that aluminac's concrete-type method lookup (`find_method_in_scope` / the scope built for `Canned`) does **not include mixin'd ext-protocol methods**. `Canned`'s `mixin Rng<Canned>` methods (`next_u32/next_u64`) resolve but `mixin RngExt<Canned>`'s `next_float` does not — so the gap is specifically in how aluminac registers/expands a *second* `mixin` (or an ext-protocol mixin whose own method has its own generic `<T: FloatingPoint>` + the `Self: Rng<Self>` super-bound). Mirror boot's `associated_fns_uncached`: when building the concrete type's method set, expand **all** mixins and fold each by name (native shadows mixin), regardless of the mixin'd protocol's super-bounds.
  2. *If aluminac still sees `R`/a placeholder at the call* (the standalone `get_float<R: Rng<R>>(rng){ rng.next_float() }` erroring at compile suggests this path exists for not-yet-substituted generics): the structural fix is eager substitution before body lowering — larger, but the #1 lookup fix likely suffices for the sysroot path since `sample` is always mono'd with a concrete `R`.

  **Diagnostic state 2026-05-15 (instrumentation-verified; stale hypotheses pruned).** Repro: a struct `Canned { mixin Rng<Canned>; mixin RngExt<Canned>; }` with only `next_u32`/`next_u64` defined directly. `c.next_u64()` (a *direct* method) resolves; `c.next(..)`, `c.shuffle(..)`, `c.next_float()` (all `RngExt` mixin methods) all fail `could not resolve method '<m>' on type 'Canned'`. Established by instrumentation:
  - **Ruled out:** proto-id extraction / `find_protocol_scope_by_id` / `process_mixins`'s copy loop. Prints in `process_mixins` show every mixin resolves its protocol scope (`scope_found=1`, non-empty item counts) — those were all *sysroot* mixins.
  - **Key redirection (instrumented):** `[DBG copy]` (in `process_mixins`, gated to `next_float`/`next_u64`) and `[DBG lookup]` (in `find_method_in_scope`) **never fired** for the `Canned` repro, yet the "could not resolve" errors did. ⟹ (1) the user-file struct's mixins are processed by **`process_mixins_from` (pass2.alu:114)**, NOT the `process_mixins` (pass2.alu:1288) that was instrumented; (2) the "could not resolve method X on type Canned" error is emitted from **`try_lower_method_call`'s own resolution/error path** (lower.alu:5910+), NOT from `find_method_in_scope` (which was never entered for these calls).

  **Next session, start here (exact targets):** instrument **`process_mixins_from`** (pass2.alu:114 — the copy loop variant that handles later/cross-file mixins; print `impl_scope_idx`, `proto_scope`, and the `next`/`next_float` item names it copies for the `Canned` repro) AND **`try_lower_method_call`** (lower.alu:5910 — print the receiver `IrTy`, the scope id(s) it searches for `c.next(..)`, and where it decides "could not resolve"). The bug is a **copy-target vs lookup-scope mismatch**: `process_mixins_from` copies `RngExt`'s methods into some scope, but `try_lower_method_call` searches a different scope for the `Canned` receiver. Fix = reconcile (have the receiver-type method search also consult the mixin-copied scope, or copy into the scope the lookup uses). - [DONE] **`.map(Result::unwrap::<...>)` through a mixin'd iterator mis-dispatches when there's no prior direct call.** **Resolved 2026-05-12.** The earlier framing (mono-context type_map pollution) was wrong on the root cause. Two underlying bugs that compounded:

  1. **`make_fn_ty` cached IrTy::Fn by source `id` alone.** Two distinct monomorphizations of the same source function (e.g. `Result::unwrap<u32, Error>` and `Result::unwrap<()>` from the panic chain) shared the same cache key, so the SECOND mono's `make_fn_ty` call hit the cache and got back the FIRST mono's fn_ref — including the first mono's `mangled_name`. Any downstream consumer of `arg_ir.ty.fn_item_ref()` then saw the wrong mangled name. Fix: key `tuple_ty_cache` on (`id`, hash of `mangled_name`) so each mono gets its own IrTy.
  2. **`ir_functions` lookups matched on `fn_ref.id` only and didn't `break` on first match.** Multiple monos of the same source function share the source `id` field, so the loops `for fi in ir_functions: if id == fn_ref.id { ret = ir_functions[fi].return_type; }` (no break) overwrote `ret` with each matching mono's return type — the LAST id-match won. In the failing case, that was the `Result::unwrap<()>` mono from the panic chain (return type `()`), not the explicitly-requested `Result::unwrap<u32, Error>` (return type `u32`). Four sites had this bug: `try_lower_method_call`'s Fn-bound inference fallback (line ~5367), the parallel Generic-bound branch (~5398), `lower_call`'s Fn/Closure return-type resolution (~5975, ~5996), and the typeop_arguments_of / typeop_return_type_of dispatchers (~498, ~531). All four now match on `(id, mangled_name)` and `break` on first match.

  The warm-up workaround (a direct `Outer::next()` call before the map chain) "worked" because it changed which monos of `Result::unwrap` existed by the time the inference ran — different ordering, different LAST match, sometimes the right return type. Pure coincidence.

  Also fixed alongside: `infer_type_args` (used by the direct-call inference path, not `try_lower_method_call`) had no case for `ExprTag::TurbofishValue` arguments. Its existing `ExprTag::FnRef` branch wouldn't fire for `Result::unwrap::<u32, Error>` (which parses as TurbofishValue, not FnRef), so U fell through unbound and the call mono'd with U=void. Added a TurbofishValue branch that snapshots/sets the function's generic params from the explicit type args, resolves the return type, then restores.

  Verified by `tests/aluminac/turbofish_fn_arg_inference.alu` (hand-rolled wrapping iterator that mirrors CharsIterator's shape and reproduces the pre-fix miscompile end-to-end) plus the 4 chars-iter unicode tests now uncfg-gated and passing under aluminac. All porting gates green.

- [DONE] **Multi-impl generic params rebind to the right ids per-method.** Aluminac (and alumina-boot) reuses a struct's shared scope across all `impl Foo<...>` blocks, so each impl block's K/V/H registers in the SAME scope and later impls overwrite earlier impls' entries by name. Pass2's `build_function` used to parse each method's parameter types against this shared scope, which left earlier impls' methods pointing at LATER impls' ids — at mono time the substitution misaligned and the call's expected type was off (concretely: under sysroot's three-impl `HashMap<K, V, H>`, declaring `HashMap<&[u8], NamedItem>` and `HashMap<u64, usize>` in the same program steered `insert(item.name, item)` to expect `u64` for the key). Fix: pass1 captures `impl_generic_param_names` alongside `impl_generic_param_ids` on `PendingFunction`; pass2's `build_function` re-registers (name, id) pairs in the method's function scope before parsing param types, so function-scope shadowing makes each method's `K` reference resolve to that impl's id. Verified by `tests/aluminac/multi_impl_generic_param_rebind.alu` (two impl blocks of the same struct with the same K/V names, run against two distinct K-type instantiations). All porting gates green.

- [DONE] **Aluminac dropped `#[cfg(...)]` on let statements.** **Fixed 2026-05-13.** `parse_let` in `src/aluminac/parser/expr.alu` didn't consult the let_declaration grammar's `attributes` field, so paired `#[cfg(A)] let x = a; #[cfg(not(A))] let x = b;` parsed both lines, registered both x ids, and the second shadowed the first via the by-name HashMap. - [DONE] **Multi-segment path resolution lost TypeAlias/GenericParam anchors.** **Fixed 2026-05-13.** `parse_scoped_identifier`'s fallback path (when `resolve_path` returns None for the full path) only checked segment[0] for GenericParam/TypeAlias. - [DONE] **Pass2's `pending` borrows survive recursive Pass1 pushes.** Every `process_X` / `process_items_from` loop in `src/aluminac/parser/pass2.alu` used to do `let pending = &self.ctx.pending_X[i]` and pass that reference into `build_X`, which then parsed the item's body / init expression. When the Vector reallocates under the push, the outer `pending` reference dangles, and subsequent reads of `pending.id` / `pending.name` / `pending.attributes` return rotted data.
