## Language features

*(Parser/AST/type system features in alumina-boot but not aluminac.)*

### Highest-leverage remaining work

The remaining compiler-side work clusters into three real items. Closing these unblocks most of the stdlib `[TODO]`s en masse; chasing stdlib files one at a time without fixing these is depth-first work against shallow leaves.

1. **~~Protocol-method Self uniformity.~~** **Resolved 2026-05-11** (commit follows this update). `build_protocol` no longer prepends the protocol's generic_params to each method — methods now have only their own generics in `def.generic_params`, matching the shape that `build_function` produces for impl methods. The protocol's generics (Self + others, in declaration order) are stored in a new `proto_method_proto_gp_ids` registry and bound at dispatch sites via `bind_proto_generics` (mixin / dyn) or `infer_proto_generics_from_call` (direct call inference). The dyn vtable build collapses to a single principled rule (no more length-arithmetic branches). `Result::unwrap` end-to-end against `--sysroot sysroot` now compiles and runs, verified by `tests/aluminac/unified_sysroot_unwrap.alu` plus a focused minimal repro that previously failed at `fmt/mod.alu:336`. mono_function's cache_key now mixes in proto-generic bindings so different instantiations don't collide on the same key when the method has no own-generics; snapshot/restore of `def.generic_params` covers method-own (the "leaky-context" behavior is preserved for proto generics — they're set by dispatchers and carry forward).
2. **Item-as-type-arg generics.** `Id`s need to flow through paths that today only handle `&IrTy`. Unblocks `proto_const` / `proto_static` / `value_of`, typeop for Static/Const, and `entrypoint_glue` migration.
3. **Reflection lang items** (~~`enum_variant_new`~~, ~~`field_descriptor_new` / `field_descriptor_new_unnamed`~~, ~~`type_descriptor_new`~~, `format_arg`). Wiring them lets the four stub intrinsics (`enum_variants`, `fields`, `vtable`, `attributed`) build their array-of-call results directly. **No const_alloc dependency** — alumina-boot's implementations are plain `array_of(...)` expressions (verified against `src/alumina-boot/src/ir/mono/intrinsics.rs`'s `intr_enum_variants`). Earlier framings in this file that linked these to `const_alloc` were wrong. **Status (2026-05-11): `enum_variant_new` / `field_descriptor_new` / `field_descriptor_new_unnamed` / `type_descriptor_new` all wired with their corresponding intrinsics (`enum_variants`, `fields`) returning real values.** Remaining: `format_arg` (used by `dyn_format_args` macro — needs unifying fmt/mod.alu which is larger), `vtable` (aluminac's existing `build_dyn_vtable_ref` is the equivalent — exposing as the intrinsic is bookkeeping), `attributed` (depends on item-as-type-arg generics, item #2). And: the `Type<T>` / `Field<S, F>` reflection structs are now in sysroot-aluminac alongside the lang items, with the standard API surface (`is_*`, `as_ptr`, etc.).
6. **~~`DefaultHashable`-via-mixin produces wrong hash.~~** **Resolved 2026-05-11.** The initial framing (mono cache pollution) was wrong. Two underlying bugs:
   - **Expression-statement attributes silently dropped the statement.** Grammar gives `expression_statement` an optional `attributes` field before the `inner` expression. Aluminac's parse_expr was iterating children and returning the first named one — which was the `attributes` node when present, leaving the actual expression unparsed. So `#[allow(unnecessary_cast)] (*field_ptr as &void as usize).hash(hasher);` became a no-op, and Quux's pointer-field hash wrote nothing. Fix: use `FieldKind::Inner` to skip past attributes. Also added `#[cfg(...)]` evaluation on expression-level attributes (factored to `ParseContext::eval_cfg_meta_item` and friends, shared with Pass1) — previously the `#[cfg(debug)]` / `#[cfg(not(debug))]` guards on sysroot's `assert!` macro were also dropped silently, so once parsing started honouring the expressions both branches got included; now the right branch is selected at parse time.
   - **`underlying_type_of<Bar>` resolved to void in sysroot-aluminac.** The typeop dispatch in mono/lower.alu was wired, but the *type alias* `type underlying_type_of<T>;` (with `#[lang(typeop_underlying_type_of)]`) wasn't declared in `sysroot-aluminac/std/builtins.alu`. Path resolution silently fell through to `void_ty`, so `Bar::A as void` and `Bar::B as void` hashed identically. Fix: copy the typeop declarations from sysroot to sysroot-aluminac (`return_type_of`, `arguments_of`, `generic_args_of`, `replace_generic_args_of`, `pointer_with_mut_of`, `array_with_length_of`, `underlying_type_of`, `underlying_function_of`, `function_pointer_of`).

   Verified by `make porting-gates`. The "standalone passes" symptom in the prior framing was misleading because the isolated test didn't exercise the enum (Bar) or the pointer-field (Quux) paths — only the Foo struct, which happened to be unaffected by both bugs. Underlying architectural issue: aluminac silently produces `void_ty` for unresolved type-alias names; tracked separately below.
4. **Per-call mono context (architectural).** Today's `type_map` is one shared mutable HashMap with leaky semantics — dispatcher paths inject bindings that downstream code depends on. The 2026-05-11 type_map-pollution fix is a targeted save/restore, and the protocol-Self-uniformity refactor extends snapshot/restore to cover proto generics — but the same kind of pollution will keep surfacing in different shapes until aluminac mirrors alumina-boot's child-mono-context model (`Mono::with_replacements` → fresh `replacements` map per call). Replacing the leaky map is a meaningful refactor of `mono/lower.alu` but it's bounded and prevents a whole class of future fixes.

   **Step taken 2026-05-11:** mono_function now snapshot/restores both `proto_method_proto_gp_ids` and `proto_method_self_id` bindings on entry/exit, on top of the existing own-generic_params save/restore. Closes the known leak points where dispatchers (`bind_proto_generics`, `infer_proto_generics_from_call`, the dyn vtable build) wrote proto generics that then persisted after mono returned. An earlier attempt at full journaling-based rollback for *all* type_map writes during body lowering surfaced a flaky segfault during the mixin_own_generics test — the journaling approach is correct in principle but interacts badly with HashMap state in a way that needs more careful diagnosis. Reverted; the targeted snapshot/restore above is the bandage we ship for now.

   **Adjacent class — id-vs-mono ambiguity (resolved 2026-05-12).** The chars-map miscompile turned out NOT to be type_map pollution — it was a different shape of "shared state across monos" bug: `make_fn_ty` cached `IrTy::Fn` by source `id` alone, and four `ir_functions` lookups (`try_lower_method_call`'s Fn-bound inference, `lower_call`'s Fn/Closure return-type, typeop_arguments_of, typeop_return_type_of) matched on `id` only and didn't break. Multiple monos of the same source fn share `id`, so distinct monos got conflated. The fix keys `make_fn_ty` on (id, mangled_name) and disambiguates lookups the same way. Listed here because it's structurally adjacent: same "compiler-wide mutable state where each mono should be distinct" failure mode that the per-call mono-context refactor would prevent class-wide.
5. **~~Macro-internal `use` doesn't reach expansion site.~~** **Resolved 2026-05-11.** Root cause: `parse_field` suppressed the UFCS hint setup (`field.id2 = function_id + 1`) when inside a macro body, so `$a.debug()` inside `macro foo($a) { use std::fmt::debug; $a.debug() }` carried no hint and the mono-time dispatch couldn't find `debug`. Dropped the `if !in_macro_body` guard. The trade-off is that names get pre-bound at definition time (matches user intent for macros that pull in helpers via `use`; the hygiene caveat is that the hint won't re-resolve at the expansion site). Verified by `tests/aluminac/macro_internal_use.alu`.
7. **~~Unresolved type-alias names silently produce `void_ty`.~~** **Partially resolved 2026-05-11.** Added a `parse_type` diagnostic at `ScopedTypeIdentifier`: when the path doesn't resolve to any known item kind, emit `unresolved type path: <path>`. Catches the DefaultHashable / `underlying_type_of` shape of bug at parse time instead of silently casting to void. Cascade-fixes that landed alongside: `populate_host_cfgs` now sets `target_env=gnu` / `target_env=musl` (previously unset, so `libc::c_char`'s cfg-gated declarations didn't fire); `sysroot-aluminac/std/panicking.alu` got a stub `internal::PanicFormatter` (referenced by sysroot's `std/result.alu`). Missing:
   - The diagnostic is `ScopedTypeIdentifier`-only. Unqualified `TypeIdentifier` failures still fall through to `Ty::unresolved` silently — same architectural gap, smaller blast radius because single-segment paths usually fail compilation at the call site instead.
   - `mono/lower.alu`'s `resolve_named_type` still ends with `self.ctx.void_ty` for items that resolve but aren't a known kind (e.g. consts / statics in type position — gated on item-as-type-arg generics, item #2).

`const_alloc` family stays a [TODO] but it's narrow-scope (heap-during-const for user code), not a hard blocker. DWARF is [DONE] (was [TODO] in error). Dyn-callable lang items are an acceptable `cfg(boot)` deviation per the project's quality bar — see PORTING.md "Specialization".

### Per-feature status

- [PARTIAL] **`dyn` / dynamic dispatch.** Real dispatch wired end-to-end for single- and multi-protocol bounds. `&T as &dyn Proto` now emits a private const global vtable (`[fn(); N]`) populated with `T`'s typed method pointers (cast to opaque `fn()`), and threads its address into the dyn fat pointer's `_vtable` slot. Method calls on dyn values load `_vtable[idx]`, cast to the typed fn pointer, and invoke with `(_ptr, args...)`. Multi-protocol bounds `&dyn (A + B + ...)` are captured (parser iterates `inner` fields, synthesizes a TupleTy; resolve_type unpacks back into the dyn struct's `Protos` type-arg). Verified by `tests/aluminac/dyn_dispatch.alu` (single-method + multi-method protocols, plus a `&dyn (A + B)` bound).

  `#[lang(dyn)]` and `#[lang(dyn_self)]` structs now exist in `sysroot-aluminac/std/builtins.alu` (sysroot puts them in `std/typing.alu`; aluminac's sysroot puts them under builtins until typing.alu is ported).

  **Structural gap closed 2026-05-11.** Earlier audits noted that the vtable build needed a fifth branch to handle protocol-default methods on builtins (e.g. `i32::fmt` mixin'd from `IntegerFormattable`). Adding a fifth branch was the wrong fix; the underlying asymmetry between `build_protocol` and `build_function` was. That asymmetry is now gone:

  - **`build_protocol` no longer prepends the protocol's generic_params** (`Self` + protocol's other generics) to each method's `generic_params`. Methods now have only their own generics, mirroring `build_function`'s shape for impl methods.
  - The protocol's generics are stored in `MonoCtx::proto_method_proto_gp_ids` (method_id → ids in declaration order, Self at index 0).
  - At dispatch sites the protocol's generics are bound into `type_map` via two complementary helpers: `bind_proto_generics(def, args)` for explicit-arg paths (mixin info, dyn proto args), and `infer_proto_generics_from_call(def, receiver, args)` for direct-call inference (mirrors what `infer_type_args` does for a function's own generics).
  - The dyn vtable build's three length-matching branches collapsed to a single principled rule: protocol-derived method → `[impl_ty, proto_args[1..]]` via `bind_proto_generics`. Plain impl methods retain the existing `[impl_args, proto_non_self_args]` arithmetic — but the case is now distinguished structurally (presence of `proto_method_proto_gp_ids` entry), not by length-coincidence.
  - `mono_function`'s cache_key mixes in the current `type_map` bindings for the proto generics, so distinct instantiations of the same protocol method (e.g. `sum<SliceIterator<i32>, i32>` vs `sum<SliceIterator<usize>, usize>`) get distinct cache entries even though `def.generic_params` is empty for both.

The wholesale-swap segfault was diagnosed and fixed: the root cause was an aluminac compiler bug in `src/aluminac/parser/pass2.alu`, not anything in the Vector code itself.

  **Root cause.** Every `process_X` / `process_items_from` loop in `pass2.alu` held a `let pending = &self.ctx.pending_X[i]` borrow into a Vector while calling `build_X(node, pending)`. Inside `build_X` (for functions, enums, statics, macros) the body / init / value expression went through `ExprParser::parse_block`, which recursively runs `Pass1::new(...).visit_node(...)` for block-local items. The recursive Pass1 can push to **the same** `pending_X` Vector — and when that push reallocates, the outer borrow dangles. Subsequent reads of `pending.id` / `pending.name` / `pending.attributes` in `build_X` then return whatever data happened to land at the freed slot, producing the corrupted `Item` shape we observed (FnDef.id = code pointer, FnDef.attributes._ptr = small integer that previously held an Attribute tag).

  The old `sysroot-aluminac/std/collections/vector.alu` reserved a minimum capacity of 4 on first allocation (`if new_cap < 4 { new_cap = 4 }`). That floor masked the bug: by the time any realloc would have fired, the small per-file pending vectors had already stabilised in the 4-slot allocation, so pushes during recursion never moved the backing storage. sysroot's vector grows tighter (max(len*2, len+additional), no floor), so pending_functions now reallocs while the outer build_function is still running — making the dangling borrow visible.

  The deterministic repro on sysroot/std/mod.alu: items 0..1 (`assume`, `panic_assert`) parsed fine; item 2 was `internal::assert` whose body contains the nested `fn panic_assert` definition. Pass2 visited assert, captured `pending = &pending_functions[2]`, started parsing the body, the recursive Pass1 pushed `panic_assert` to `pending_functions`, the Vector realloc'd from capacity 4 to 8, and the outer `pending` reference became stale. `assert`'s FnDef.id / .name / .attributes / .span fields were then read off freed memory; build_lookup_tables later iterated those rotted attributes and segfaulted dereferencing a fake _ptr.

  **Fix.** `src/aluminac/parser/pass2.alu`'s 12 `process_X` / `process_items_from` / `process_macros_from` / `process_mixins*` loops now copy `pending` by value (`let pending = self.ctx.pending_X[i]`) instead of borrowing. The local snapshot survives realloc; `build_X(node, &pending)` then takes a borrow into the local copy, which is valid for the duration of the call. The `for i in ..len()` headers were rewritten as explicit `loop { if i >= len { break } ... i += 1 }` because the `for-in` lowering captures the range by value at iter time; we want fresh `.len()` reads in case nested recursion grows the Vector.

- [DONE] **`.map(Result::unwrap::<...>)` through a mixin'd iterator mis-dispatches when there's no prior direct call.** **Resolved 2026-05-12.** The earlier framing (mono-context type_map pollution) was wrong on the root cause. Two underlying bugs that compounded:

  1. **`make_fn_ty` cached IrTy::Fn by source `id` alone.** Two distinct monomorphizations of the same source function (e.g. `Result::unwrap<u32, Error>` and `Result::unwrap<()>` from the panic chain) shared the same cache key, so the SECOND mono's `make_fn_ty` call hit the cache and got back the FIRST mono's fn_ref — including the first mono's `mangled_name`. Any downstream consumer of `arg_ir.ty.fn_item_ref()` then saw the wrong mangled name. Fix: key `tuple_ty_cache` on (`id`, hash of `mangled_name`) so each mono gets its own IrTy.
  2. **`ir_functions` lookups matched on `fn_ref.id` only and didn't `break` on first match.** Multiple monos of the same source function share the source `id` field, so the loops `for fi in ir_functions: if id == fn_ref.id { ret = ir_functions[fi].return_type; }` (no break) overwrote `ret` with each matching mono's return type — the LAST id-match won. In the failing case, that was the `Result::unwrap<()>` mono from the panic chain (return type `()`), not the explicitly-requested `Result::unwrap<u32, Error>` (return type `u32`). Four sites had this bug: `try_lower_method_call`'s Fn-bound inference fallback (line ~5367), the parallel Generic-bound branch (~5398), `lower_call`'s Fn/Closure return-type resolution (~5975, ~5996), and the typeop_arguments_of / typeop_return_type_of dispatchers (~498, ~531). All four now match on `(id, mangled_name)` and `break` on first match.

  The warm-up workaround (a direct `Outer::next()` call before the map chain) "worked" because it changed which monos of `Result::unwrap` existed by the time the inference ran — different ordering, different LAST match, sometimes the right return type. Pure coincidence.

  Also fixed alongside: `infer_type_args` (used by the direct-call inference path, not `try_lower_method_call`) had no case for `ExprTag::TurbofishValue` arguments. Its existing `ExprTag::FnRef` branch wouldn't fire for `Result::unwrap::<u32, Error>` (which parses as TurbofishValue, not FnRef), so U fell through unbound and the call mono'd with U=void. Added a TurbofishValue branch that snapshots/sets the function's generic params from the explicit type args, resolves the return type, then restores.

  Verified by `tests/aluminac/turbofish_fn_arg_inference.alu` (hand-rolled wrapping iterator that mirrors CharsIterator's shape and reproduces the pre-fix miscompile end-to-end) plus the 4 chars-iter unicode tests now uncfg-gated and passing under aluminac. All porting gates green.

- [DONE] **Multi-impl generic params rebind to the right ids per-method.** Aluminac (and alumina-boot) reuses a struct's shared scope across all `impl Foo<...>` blocks, so each impl block's K/V/H registers in the SAME scope and later impls overwrite earlier impls' entries by name. Pass2's `build_function` used to parse each method's parameter types against this shared scope, which left earlier impls' methods pointing at LATER impls' ids — at mono time the substitution misaligned and the call's expected type was off (concretely: under sysroot's three-impl `HashMap<K, V, H>`, declaring `HashMap<&[u8], NamedItem>` and `HashMap<u64, usize>` in the same program steered `insert(item.name, item)` to expect `u64` for the key). Fix: pass1 captures `impl_generic_param_names` alongside `impl_generic_param_ids` on `PendingFunction`; pass2's `build_function` re-registers (name, id) pairs in the method's function scope before parsing param types, so function-scope shadowing makes each method's `K` reference resolve to that impl's id. Verified by `tests/aluminac/multi_impl_generic_param_rebind.alu` (two impl blocks of the same struct with the same K/V names, run against two distinct K-type instantiations). All porting gates green.

- [DONE] **Pass2's `pending` borrows survive recursive Pass1 pushes.** Every `process_X` / `process_items_from` loop in `src/aluminac/parser/pass2.alu` used to do `let pending = &self.ctx.pending_X[i]` and pass that reference into `build_X`, which then parsed the item's body / init expression. The body parse goes through `ExprParser::parse_block`, which runs a recursive `Pass1::new(...).visit_node(...)` for block-local items — and that recursion pushes to the same `pending_X` Vector. When the Vector reallocates under the push, the outer `pending` reference dangles, and subsequent reads of `pending.id` / `pending.name` / `pending.attributes` return rotted data. The 12 loop sites now snapshot pending entries by value (`let pending = self.ctx.pending_X[i]; build_X(node, &pending)`), so the local copy survives realloc. Surfaced by the std/collections/vector.alu wholesale swap (sysroot's tighter Vector growth removed the old `min 4` capacity floor that had been masking the bug); verified by `tests/aluminac/nested_fn_pending_realloc.alu` plus all 5 previously-segfaulting `--sysroot sysroot` tests now passing.
